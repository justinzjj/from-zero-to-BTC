## 一、基础知识

### 1. UTXO 与当前可花资金表

Alice 想付给 Bob 60000 聪。先看付款前节点已有的三条记录。**一条尚未被花费的交易输出就是一个 UTXO**。这里把当前 UTXO 集合画成表，每行对应一条输出。U、V、W 和下文的 B 都是虚构交易 ID 的简称，高度和金额也是课堂构造的数据。

#### 付款前 · 三条记录

| 创建交易 txid | 输出序号 vout | 金额（聪） | 花费条件 | 创建高度 | 来自 coinbase |
|---|---|---:|---|---:|---|
| U | 0 | 100000 | Alice 的花费条件 | 900000 | 否 |
| V | 0 | 20000 | Alice 的花费条件 | 900001 | 否 |
| W | 0 | 8000 | Bob 的花费条件 | 900002 | 否 |

钱包认出前两条输出的脚本与 Alice 的密钥对应，在本例条件下算出她有 120000 聪；Bob 有 8000 聪。节点只需保存各笔输出及其条件，无需把地址归并到一个人名下。Alice、Bob 是帮助读表的标签。真实交易写入脚本，并无姓名或通用收款编号字段。

**“未花费”只说明当前还没有交易消耗这条输出。** 真要花费，还须满足授权等适用条件。coinbase 是区块中领取奖励与手续费的特殊交易，其输出还受成熟期规则约束。行与列在这里用来说明查找和更新的语义；本课不需要关系型数据库或 SQL。[Core v29.0 · Coin](https://github.com/bitcoin/bitcoin/blob/v29.0/src/coins.h)

### 2. OutPoint 与联合主键

输入写“第 0 条”能找到哪笔钱？表里三行的序号都是 0。若只写创建交易的 txid，同一交易又可以产生多条输出。**两列合在一起才唯一：OutPoint = (txid, vout)**。U:0 读作“交易 U 创建的第 0 个输出”。vout 是创建交易输出列表中从 0 开始的序号；即使记录在数组里搬到另一个槽位，这个引用也不变。[Core v29.0 · COutPoint](https://github.com/bitcoin/bitcoin/blob/v29.0/src/primitives/transaction.h#L25-L47)

### 3. 交易输入、输出与整笔状态更新

Alice 的钱包只选 U:0。先读它提交的付款 B，再观察节点使用哪份数据核验金额。下表只列本课关注的字段。

#### B 的输入

| 输入序号 | 引用的创建交易 | 引用的输出序号 | 按键到哪里取值 |
|---|---|---|---|
| 0 | U | 0 | 从 U:0 读取金额和旧花费条件 |

#### B 的输出

| 在 B 中的序号 | 金额（聪） | 花费条件 | 钱包对用途的判断 |
|---|---:|---|---|
| 0 | 60000 | Bob 的花费条件 | 收款 |
| 1 | 39000 | Alice 的花费条件 | 找零 |

两个新输出的格式相同，序号由排列位置决定。交易里没有“找零”字段。金额从引用的旧输出取得；输入不能自行声称“我值 120000 聪”。

#### 付款过程

| 步骤 | 动作 | 本例的结果 |
|---|---|---|
| 1 构造 | 钱包选择输入并填写输出 | 引用 U:0，给 Bob 60000，找零 39000 |
| 2 查找 | 节点同时比较 txid 和 vout | U:0 命中，V:0、W:0 不参与 |
| 3 读取 | 从旧记录取金额与条件 | 100000 聪，须满足 Alice 的花费条件 |
| 4 检查 | 检查存在性、重复引用、金额范围等 | 真实节点还核验授权、成熟期等适用规则 |
| 5 核算 | 输入总额减去输出总额 | 100000 − 99000 = 1000 聪手续费 |
| 6 更新 | 全部检查通过，整笔应用 | 消耗 U:0，新增 B:0、B:1，保留 V:0、W:0 |
| 7 再花费 | Bob 下次引用新收到的 60000 | 填 B:0；重新查 U:0 会失败 |

#### 付款后 · 四条记录

| 创建交易 txid | 输出序号 vout | 金额（聪） | 花费条件 | 创建高度 | 来自 coinbase |
|---|---|---:|---|---:|---|
| V | 0 | 20000 | Alice 的花费条件 | 900001 | 否 |
| W | 0 | 8000 | Bob 的花费条件 | 900002 | 否 |
| B | 0 | 60000 | Bob 的花费条件 | 900003 | 否 |
| B | 1 | 39000 | Alice 的花费条件 | 900003 | 否 |

假设包含普通付款 B 的区块高度为 900003。两个新输出都从该区块取得创建高度，coinbase 标记均为 false。**U:0 被整条消耗；39000 聪属于新键 B:1。** 钱包此时算出 Alice 有 59000 聪，Bob 有 68000 聪。两人的合计减少了 1000 聪；这笔付款只有两条输出。任一检查失败，保留原表。

广播和进入本地交易池只表示待确认。节点连接活动链区块时才按块内顺序应用交易；U:0 从当前表消失，区块中的历史交易 U 仍然存在。课堂的 apply() 直接模拟这次更新，区块连接留给后续课。第 04 讲才接入授权验证，因此本课的成功回执不能证明付款人有权花 U:0。[Core v29.0 · UpdateCoins](https://github.com/bitcoin/bitcoin/blob/v29.0/src/validation.cpp)

### 4. COutPoint、CTxOut、Coin 与输出字节

怎样将表格的一行对应到真实代码？在 Core v29.0 的逻辑视图中，**COutPoint（键）→ Coin（值）**，其中 Coin.out 是 CTxOut。键放在集合一侧，Coin 本身不含 OutPoint。输出自身只写金额与脚本；其 txid 和序号由创建交易及位置确定。一行只需要定位并检查这笔旧输出，无须保存完整交易。

#### 真实字段表

| 所属对象 | 字段 | 类型 | U:0 的示例值 | 来自哪里 | 用来做什么 |
|---|---|---|---|---|---|
| COutPoint | hash | Txid，32 字节 | U | 创建交易的 txid | 定位哪笔交易 |
| COutPoint | n | uint32_t | 0 | 输出在交易中的位置 | 定位哪条输出 |
| CTxOut | nValue | CAmount，int64_t | 100000 聪 | 创建交易的输出 | 核对可用金额 |
| CTxOut | scriptPubKey | CScript，变长 | Alice 的 P2WPKH 脚本 | 创建交易的输出 | 规定花费条件 |
| Coin | out | CTxOut | 上述金额与脚本 | 创建交易的对应输出 | 验额、取旧条件 |
| Coin | nHeight | uint32_t，31 位域 | 900000 | 包含 U 的区块 | 结合高度检查成熟期等 |
| Coin | fCoinBase | unsigned int，1 位域 | false | U 是否为 coinbase | 判定是否适用成熟期 |

地址是钱包展示和接收付款请求时使用的编码。以 P2WPKH 为例，钱包由地址取得见证版本和程序，把 20 字节公钥哈希写进输出脚本；哈希只是脚本的一部分。将来花费该输出时，花费交易通过见证提供签名和公钥。其他输出类型的授权材料和提供方式可以不同。[Core v29.0 · CTxOut](https://github.com/bitcoin/bitcoin/blob/v29.0/src/primitives/transaction.h) · [BIP 141 · P2WPKH](https://bips.dev/141/#p2wpkh)

#### P2WPKH 输出的网络序列化

取 U:0 的 100000 聪，构造一段符合格式的输出字节。用从 00 到 13 的 20 个字节填公钥哈希；这是一组演示数据，没有对应的链上交易。下表字节均为十六进制。

| 输出中的字段 | 长度 | 完整字节 |
|---|---|---|
| nValue，小端整数 | 8 字节 | a0 86 01 00 00 00 00 00 |
| scriptPubKey 长度，CompactSize | 1 字节 | 16 |
| scriptPubKey，版本 0 与公钥哈希 | 22 字节 | 00 14 00 01 02 03 04 05 06 07 08 09 0a 0b 0c 0d 0e 0f 10 11 12 13 |

把三行从上往下连接即为完整输出。外层 0x16 = 22，框住**整段脚本**；脚本内的 0x00 表示见证版本 0，0x14 = 20，后接 **20 字节哈希**。总长 8 + 1 + 22 = **31 字节**。这只是一条输出的网络编码；不含创建高度、coinbase 标记、输出序号或整笔交易的输入输出计数。[Bitcoin 交易格式](https://developer.bitcoin.org/reference/transactions.html) · [BIP 141](https://bips.dev/141/)

**同一条记录的三种表示。** 网络编码用于交换交易；内存中的 CTxOut/Coin 使用 C++ 对象、变长脚本和元数据；chainstate 落盘时另行编码键和值。因此不能用这 31 字节推算单条 UTXO 的数据库占用。补充阅读：交易输入里的 OutPoint 用 32 字节标识加固定 4 字节小端序号，Core v29.0 数据库键则含记录前缀、哈希及 VARINT 序号；值侧组合高度和标记，对金额、脚本使用专门的压缩序列化。[CoinEntry](https://github.com/bitcoin/bitcoin/blob/v29.0/src/txdb.cpp#L36-L41) · [Coin 序列化](https://github.com/bitcoin/bitcoin/blob/v29.0/src/coins.h) · [TxOutCompression](https://github.com/bitcoin/bitcoin/blob/v29.0/src/compressor.h)

#### 交易结构与付款构造

已经确定教学账本保留哪些字段。现在把“花费 U:0，给 Bob 60000 聪，给 Alice 找零 39000 聪”写成一笔交易。

| 付款意图 | 交易中的位置 | 填入的数据 |
|---|---|---|
| 花费一条旧输出 | vin[0].previous | U:0 |
| 给 Bob 付款 | vout[0] | 金额 60000，收款标识 2 |
| 给 Alice 找零 | vout[1] | 金额 39000，收款标识 1 |
| 输入和输出数量 | input_count / output_count | 1 / 2 |

在 [lab03.cpp](../../code/lesson-03/lab03.cpp) 中，调用者把 U:0 作为参数 old 传给 payment。对照赋值表逐行读：

```cpp
static Transaction payment(OutPoint old) {
    Transaction tx;
    tx.input_count = 1;
    tx.vin[0].previous = old;
    tx.output_count = 2;
    tx.vout[0] = {60000, 2};
    tx.vout[1] = {39000, 1};
    return tx;
}
```

函数返回一笔交易，描述想花哪条旧记录、想创建哪些新输出。**此时账本还没有变化。** 用交易 ID B 给新输出命名，两条分别为 B:0 和 B:1。输入只写了 U:0；节点还要查账才能知道它是否存在、里面有多少钱。

### 6. 查找、检查与状态更新算法

#### OutPoint 查询与旧输出读取

交易输入中的 U:0 → 按 txid 和输出序号查询 → 找到旧输出 → 读取金额与花费条件。

| 步骤 | 当前数据 | 执行操作 | 得到什么 |
|---|---|---|---|
| 读取输入 | tx.vin[0].previous | 取出查询键 | U:0 |
| 查找账本 | UTXO 表中的各条记录 | 同时比较完整 txid 和输出序号 | 匹配行的位置 slot |
| 找到记录 | coins[slot].output | 读取旧输出 | 100000 聪、Alice 的教学收款标识 1 |
| 没找到 | slot == -1 | 拒绝交易 | 账本保持不变 |

[Ledger::find](../../code/lesson-03/ledger.cpp) 的循环实现表中的查找步骤：

```cpp
int Ledger::find(const OutPoint& key) const {
    for (int i = 0; i < count; ++i) {
        if (same_key(coins[i].key, key)) return i;
    }
    return -1;
}
```

same_key 比较完整 txid 和输出序号。slot 是当前数组位置；OutPoint 的序号是输出在创建交易中的位置。最坏要比较 n 行，查询只读。调用者必须先排除 −1 才能访问数组。查无此键只说明当前视图缺少这条可用记录，无法仅据此区分从未存在和已经花费。

**输入提供引用，金额从节点自己的账本取得。** 真实 Bitcoin 还读取旧输出的 scriptPubKey。教学代码暂以 recipient 标记收款人，第 04 讲接入授权检查。

#### 重复输入检查

找到 U:0 只说明它存在。若同一笔交易的两个输入都引用它，在同一份未改动的账本上分别查询都会成功，因此还要检查输入是否重复。

对第 k 个输入，先比较 vin[0..k−1] 的键，遇到相同键立即拒绝；随后才计入金额。这样，输入前缀就充当已见集合。花费两个不同序号则允许。对 i 个输入、n 条记录，输入查找 O(in)，前缀比较 O(i²)，额外空间 O(1)。账本预留 C 个槽位，占 O(C)，这里 C=4；有效键在集合中始终唯一。

#### 金额范围、找零与手续费

Alice 希望收款人拿到 60000，自己留下 39000。固定旧输入后，钱包如何为两个输出定额，节点又如何核对？钱包可以从预算反推找零：100000 − 60000 − 1000 = 39000。对节点，两条输出地位相同，交易没有“找零”标志。节点从旧币累计 I，从新输出累计 O，再要求 **I ≥ O，fee = I − O**。本例 O = 99000，fee = 1000 聪。**手续费是差额，这笔付款只有两个输出，没有给矿工另建输出。**

金额单位为整数聪，允许零。每项以及输入、输出各自的累计值都必须在 [0, MAX_MONEY]，上限为 21000000 × 100000000 聪。累计器 total 从 0 开始：先拒绝 value < 0，再检查 value > MAX_MONEY − total，余量够才加。由此前缀和始终合法，避免先做有符号溢出再比较。最后仅在 O ≤ I 时做减法。查到旧币后的加法与比较耗时 O(i+o)，额外空间 O(1)。

把付款改为 62000，找零仍为 39000，合计 101000，会拒绝。只改为 61000，合计恰好 100000，手续费变成零，金额规则允许。**满足金额规则不能证明付款符合 Alice 的意愿。** Core 在 CheckTransaction 检查输出范围、累计和与输入重复，在 CheckTxInputs 利用 UTXO 检查输入价值和费用；范围属于共识约束，课堂的预加法写法是实现选择。[MoneyRange](https://github.com/bitcoin/bitcoin/blob/v29.0/src/consensus/amount.h) · [CheckTransaction](https://github.com/bitcoin/bitcoin/blob/v29.0/src/consensus/tx_check.cpp) · [Consensus::CheckTxInputs](https://github.com/bitcoin/bitcoin/blob/v29.0/src/consensus/tx_verify.cpp)

#### UTXO 状态转移与顺序执行

如果查到第一个输入就删掉它，第二个输入缺失怎么办？**先把整笔交易检查完，再写任何一行。** 前面的检查通过后，计算更新后的条数 n−i+o，超过 C 就拒绝；构造新键 (B,j)，逐一检查与当前记录无冲突。同一 B 内的序号 j 天然互异。这条保守的防覆盖检查和四行上限都是本实验的约束。

输入键列表描述要删除的集合，(B,j) 与 vout[j] 描述要新增的集合，合起来就是本笔状态变更。每次删除重新按键定位，将末行搬入空位，再缩短有效长度；最后顺序追加新行。**旧键消失，新键各出现一次，其余记录的键和值不变。** 对只有一笔普通付款的视图，总额减少 fee。单线程 apply 内部重新调用 check，实际修改段只有定长赋值，无须复制整本账或事后修补。交易按提交顺序生效，返回的槽位不能跨更新缓存。

包含新键查找与编码在内，总耗时 O(i² + (i+o)n + L)，临时编码 O(L)，删除或追加本身只需常数额外空间。Core 在 UpdateCoins 中通过缓存消费输入并加入输出；Coin 还考虑 coinbase 等元数据。这里仅检查可花状态与金额，**知道别人的 outpoint 就能构造盗花交易**。第 04 讲须在改动账本前用旧输出的花费条件核对授权。本课未实现脚本、完整签名摘要、交易池、区块、网络及持久化。[validation.cpp · UpdateCoins](https://github.com/bitcoin/bitcoin/blob/v29.0/src/validation.cpp) · [coins.cpp · SpendCoin、AddCoins](https://github.com/bitcoin/bitcoin/blob/v29.0/src/coins.cpp)

### 拓展理解｜Bitcoin 的 UTXO 模型与 Ethereum 的账户模型

**如果 Alice 付给 Bob 60000，节点到底改了哪几条记录？** 先看两种账本如何表示同一件事，再回到真实系统追踪费用、确认和授权。这部分用于读图与讨论，实践仍只实现前面的最小 UTXO 账本。

#### 同一笔付款，两种状态转移

**忽略费用的教学对照。** 两边都用与聪等值的抽象教学单位，初始 Alice 有 100000，Bob 有 0。这里没有做 BTC 与 ETH 的汇率换算。此处单独比较主例选中的 100000，暂略双方另外两条旧收入。假设 Alice 的下一笔账户交易序号为 7。

```text
                        执行前                 付款动作                   执行后
UTXO 集合               U:0  100000       →   整笔消费 U:0       →   B:0   60000  Bob
                                                                    B:1   40000  Alice
账户余额与发送序号       Alice 100000 / 7  →   Alice 发送 60000   →   Alice 40000 / 8
                        Bob        0          交易携带 nonce 7       Bob   60000
```

看两处 **40000**。在第一行的 UTXO 模型里，Alice 下一次要花的是一个全新的键 B:1。在账户模型里，她下一次仍从原地址付款，签入新的 nonce。Bob 单纯收款不会增加他的发送序号。下文回到真实 Bitcoin 示例时恢复 **1000 聪手续费**，找零随之变为 **39000 聪**。

#### 从钱包发现 U:0 到活动链确认 B

1. **发现资金。** 钱包同步区块或重扫已有区块，将输出脚本与自己跟踪的收款、找零条件匹配。看到 U 的第 0 个输出匹配后，钱包记录相关交易、序号和金额，再跟踪是否已有交易花它。假设它已经确认、Alice 有相应密钥且无待确认冲突，钱包可把这 100000 聪列入可选资金。钱包显示的可用余额受确认、锁定和待确认付款影响；节点的 UTXO 视图按键保存全网当前链上的未花费记录，无需知道哪几个地址属于 Alice。[开发指南 · 钱包](https://developer.bitcoin.org/devguide/wallets.html) · [Core v29.0 · SyncTransaction](https://github.com/bitcoin/bitcoin/blob/v29.0/src/wallet/wallet.cpp#L1310-L1319)
2. **指定资金与去向。** 钱包用旧交易的 txid 和从零起算的输出序号 vout 构成输入引用 U:0。新输出 B:0 记录 60000 聪及 Bob 的花费条件，B:1 记录 39000 聪及 Alice 的找零条件。“锁给地址”是钱包界面的简称：钱包由地址构造输出脚本 scriptPubKey，将来花费者必须提供满足条件的数据。节点从旧记录取出输入金额。100000 − 60000 − 39000 = 1000 聪，交易到此只有两个输出。[开发指南 · 交易](https://developer.bitcoin.org/devguide/transactions.html) · [Core v29.0 · CTxIn 与 CTxOut](https://github.com/bitcoin/bitcoin/blob/v29.0/src/primitives/transaction.h)
3. **广播与待确认。** 接收节点以自身可见的链状态和交易池依赖为背景，检查输入是否存在、是否冲突、授权数据能否满足旧脚本，以及金额、锁定时间等适用规则。进入本地交易池还须满足本节点策略。此时钱包可以把 U:0 标为待花；B 也可能被替换或移出池。**仅广播或入池不会从活动链视图删除 U:0。** 不同节点可以暂时看到不同的待确认交易。[Core v29.0 · 验证与交易池接纳](https://github.com/bitcoin/bitcoin/blob/v29.0/src/validation.cpp)
4. **连接区块与重组。** 节点验证并连接包含 B 的区块时，按区块内顺序消费 U:0，加入 B:0、B:1；之后若同块还有交易花 B:0，就继续消费它。历史仍记载 U 和 B，本次状态更新只移除已花的记录。若包含 B 的区块因重组退出活动链，节点撤销被断开区块的更新，再按新分支执行。U:0 最终是否可花，取决于新分支是否也花了它。**查表能判断一条既定历史上的双花；出现两条各自有效的分支时，还须按共识规则在有效链中选择累计工作量最大的链。** [开发指南 · 区块链](https://developer.bitcoin.org/devguide/block_chain.html) · [Core v29.0 · UpdateCoins、DisconnectBlock](https://github.com/bitcoin/bitcoin/blob/v29.0/src/validation.cpp)

#### 从一个输入到十个输入，哪些事变容易，哪些事变贵？

| 机制 | 在这笔付款中有什么用 | 在什么条件下成立 |
|---|---|---|
| 旧输出有唯一引用 | 节点拿 U:0 找到确切来源，直接核对这笔资金是否仍在 | 必须指定同一链状态；只有缺失结果时，不能判断它曾经存在还是从未存在 |
| 交易列出全部输入 | 若另一笔付款也写 U:0，比对两组键就能指出冲突 | 单笔内也要去重；冲突本身不能决定哪笔最终确认 |
| 输入取旧值，输出写新值 | 节点独立算出 1000 聪差额，无须相信钱包报出的手续费 | 输入必须可用且唯一，累计金额还须合法 |
| 输入彼此独立 | 两笔花不同旧币的交易，有机会同时检查各自的授权 | 须备齐旧币；子交易即使输入键与父交易不同，也要等父输出产生。验证结果和提交顺序仍须与区块规则一致 |
| 每个输出可设独立条件 | Alice 可以给不同用途的收款使用不同地址，单独选用某笔收入 | 钱包须管理好相应密钥。链上仍公开输入与输出，地址分开不足以保证匿名 |

**若 100000 聪分散在十笔收入里**，钱包要选出能覆盖 60000 聪及费用的一组，决定是否找零、找到哪里。与一笔大输入相比，多笔同类输入通常意味着更多引用和授权数据，交易虚拟大小增加；目标费率相同时，为获得相同费率通常要付更多费用。因此，“余额够”回答不了“付款要花多少手续费”。选币算法属于钱包的工程选择。[Core v29.0 · AvailableCoins 与交易构造](https://github.com/bitcoin/bitcoin/blob/v29.0/src/wallet/spend.cpp)

小输出有两笔不同的账要算。钱包按当前目标费率估算：额外加入这枚币所增加的费用，会不会吃掉币值？节点判断 **dust（尘埃）** 时，Core v29.0 则按该输出的大小、估算的花费大小和配置的 dust 转发费率计算策略门槛。一个高于门槛的输出，在费率高时也可能不值得花。该门槛用于本地策略，不能拿来判定区块共识有效性。[Core v29.0 · GetDustThreshold、IsDust](https://github.com/bitcoin/bitcoin/blob/v29.0/src/policy/policy.cpp#L22-L60)

**同一组选择也影响节点和旁观者。** 长期留下大量未花小输出会扩大节点要保存、缓存和按键查询的集合。把多笔收入合并为输入，旁观者就可能推测它们受共同控制；识别出疑似找零，还可能把 Alice 的新旧活动联系起来。多人协作交易说明这些推断并非身份证明。若应用要维护一个多方可更新的计数器，输出也可以承载花费条件，但设计者须安排怎样消费旧状态、约束后继状态、处理同时争用同一输出的更新；可表达的约束还取决于链的脚本能力。[开发指南 · 交易与隐私](https://developer.bitcoin.org/devguide/transactions.html) · [Bitcoin 合约示例](https://developer.bitcoin.org/devguide/contracts.html)

#### Ethereum 的账户、nonce 与持续存储

回到无费用图，设双方都是普通外部账户。Alice 签的交易包含目的地址、金额和 **nonce 7**。在发送者当前 nonce 为 7、签名和可用余额等条件满足时，执行成功后 Alice 扣款、Bob 入账，Alice 的 nonce 变为 8。再次交来原签名，签名仍可核验，但序号已经过期。带 8 的交易也不能在链上抢先于 7 执行。这解释了同一发送者的排序和**同一条链上**的重放检查。Bitcoin 则通过检查旧输出是否仍存在，限制那笔资金再次被使用。[Ethereum 账户](https://ethereum.org/en/developers/docs/accounts/) · [Ethereum 交易](https://ethereum.org/en/developers/docs/transactions/)

**真实 ETH 转账还要付执行费用。** 对普通 EIP-1559 转账，发送者需有足够余额覆盖转账金额及规定的费用预算；实际执行费按已用 gas × 有效 gas 单价结算。基础费部分销毁，优先费归区块提议者。gas 上限是预算，不能直接当作已用量。Bitcoin 的付款费用已经由输入输出差额确定，钱包通常按目标费率与预计虚拟大小来选这个差额。两者的计量对象和结算方式不同。[Ethereum gas 与费用](https://ethereum.org/en/developers/docs/gas/)

账户状态除余额、nonce 外，还有代码哈希和与持久存储对应的存储根。想象一个合约在固定地址保存“已售票数”。一次调用读取 17 并写回 18，下一次调用可到同一地址读到 18。这种编程方式让持续状态有稳定的访问位置，也带来约束：两次售票若都读取 17，执行器必须处理读写冲突，产生与规定交易顺序相同的结果。不同发送者也可能争用同一合约，持续写入新数据还会增加节点状态负担。Ethereum 采用账户模型适配这类状态读写；**PoS 负责就链的历史达成共识，账户模型规定给定历史如何更新状态**，两者是不同设计维度。[Ethereum 白皮书 · 账户与状态转移](https://ethereum.org/en/whitepaper/) · [Ethereum 账户字段](https://ethereum.org/en/developers/docs/accounts/)

| 对照项 | Bitcoin 的 UTXO 模型 | Ethereum 的账户模型 |
|---|---|---|
| 资金表示 | 一组带金额、花费条件的未花输出 | 地址对应账户，账户保存余额 |
| 付款引用 | 输入逐笔点名 txid + vout | 签名确定发送者，交易给出目的地址、金额、发送 nonce |
| 状态更新 | 消耗旧输出，创建收款与找零输出 | 普通转账更新双方余额和发送者 nonce |
| 余额计算 | 钱包筛出自己可用的输出并求和 | 可在指定链状态直接读取账户的原生 ETH 余额 |
| 重复花费／重放检查 | 同笔输入唯一，所引输出仍可用 | 交易 nonce 须匹配该发送者的当前 nonce |
| 费用相关因素 | 差额定费用；费率与虚拟大小影响构造 | 执行消耗 gas，按有效 gas 单价结算 |
| 合约状态表达 | 消费旧输出、通过条件约束状态变更，受脚本能力限制 | 合约地址、代码及持续可读写的存储 |
| 并行处理约束 | 检查输入冲突、父子依赖，保证应用顺序正确 | 同一发送者有序；共享账户或合约存储也可能冲突 |

### 2. 从测试记录到执行回执

先用[付款推演单](resources/付款推演.txt)写下预测，再逐项对照程序。

2. **构造付款。** 在 payment 里找到 vin[0].previous 和两行 vout。先写出两个输出各自的序号；尝试交换两行，预测收款与找零将对应哪个新键。
3. **检查并提交。** check 读账本，计算输入 100000、输出 99000、差额 1000。apply 对当前内容重查，正常打印 `ACCEPT fee=1000`。

#### 实践读数：教学交易 v3 的编码与标识

为了给新输出命名，先得算出创建它的交易标识 B。**教学格式 v3** 按下列顺序逐字段写入。多字节整数一律小端，摘要用原始 32 字节顺序。记输入数为 i，输出数为 o，则字节数 L = 3 + 36i + 12o，本例为 63。版本字节 03 是本课程约定。第 01 讲的 13 字节 v1 草稿、02A 的 12 字节签名练习均缺少旧输出引用，不能直接提交给账本。

```text
版本(1) → i(1) → i × [旧 txid(32), 序号(4)]
        → o(1) → o × [金额(8), 收款标识(4)]
B = SHA256(SHA256(上述完整字节))
```

同一字段序列得到同一 B；交换两个输出就改变编码和输出位置。编码与哈希耗时 O(L)，字节缓冲占 O(L)。**不要哈希结构体内存**：数组空位、机器字节序、对齐填充都可能不同。摘要能标识内容，不能证明是谁构造它。Bitcoin 的 CTxIn 还有 scriptSig、sequence，CTxOut 保存金额和 scriptPubKey；实际交易使用版本、CompactSize 计数、锁定时间等。Bitcoin txid 对不带见证的交易序列化做双 SHA-256，课堂保留哈希算法，改用上述字段。[transaction.h · COutPoint、CTxIn、CTxOut](https://github.com/bitcoin/bitcoin/blob/v29.0/src/primitives/transaction.h) · [transaction.cpp · ComputeHash](https://github.com/bitcoin/bitcoin/blob/v29.0/src/primitives/transaction.cpp)

### 3. 失败与保证边界

| 改哪一处 | 预期结果 | 验证点 |
|---|---|---|
| 成功后重放原交易；或第二个输入指向 U:99 | missing or spent | 当前集合没有这个键 |
| 同笔内两次填 U:0 | duplicate input | 不能重复计入 100000 |
| 预检成功再改 60000 为 62000 | overspend | apply 不接受旧回执来跳过检查 |
| 负金额、MAX_MONEY+1、累计越界、可能使 int64 溢出的加数 | output range | 每次加法前比较剩余额度 |
| 输入或输出计数取 −1、0、5 | input count / output count | 读数组前拒绝 |
| 账本有两条，花一条，建四条 | ledger full | 五条放不下；建三条则恰好填满 |
| read 给越界槽位；修改合法 read 的返回副本 | false；原账本保持原值 | 外部不能借查询绕开 apply |
| 从初始状态只改收款人 2 为 9 | ACCEPT，摘要改变 | 未检查授权；哈希改变并不等于交易会被拒绝 |

完整预期输出含固定摘要和每条拒绝原因，见[实测输出](resources/正常与失败输出.txt)。运行最后应出现 `ALL CHECKS PASSED`。练习时另建一份 tx 试改，保留原验收样例作为对照。

### 4. 规模观察、验收与下游接入

求余额要扫描全部 n 行，只累加属于 Alice 的输出。时间 O(n)，游标和累计值只占 O(1) 额外空间。

`std::map` 可用平衡树提供 O(log n) 查询；哈希表平均 O(1)，最坏 O(n)，还要保存索引等额外数据。本课用固定数组便于逐项观察。同一套可花性规则可以配不同容器。Core 的 CCoinsViewCache 按 outpoint 访问分层视图，CCoinsMap 使用哈希映射；缓存和刷盘方式属于实现选择。[coins.h · CCoinsMap、CCoinsViewCache](https://github.com/bitcoin/bitcoin/blob/v29.0/src/coins.h)

把二进制单独交给 `time ../../code/build/lesson-03/lab03`，记录机器、编译选项及多次结果；该数包含启动、打印与断言。若只观察查询成本，可在 find 的循环内计数，分别查首行、末行、缺失键，预测比较 1、n、n 次。输出的 sizeof 反映当前编译器的内存布局，可与本例 63 字节编码比较；固定数组容量调大时，即使只填一个输入，内存对象也会变大。库版本和实测数据见[验证记录](resources/验证记录.txt)。
