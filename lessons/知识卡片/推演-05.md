# 逐步执行脚本并检查归属

P2WPKH 的全称是 Pay to Witness Public Key Hash。创建输出时，付款钱包留下一个公钥哈希。后来有人花这项输出，节点才检查公钥和签名。

## 脚本怎样让钱包认出「这项输出与我有关」？

脚本是按 Bitcoin Script 规则解释的一串字节。操作码描述动作，紧随压栈指令的字节可以携带数据。每个交易输出都有金额和 scriptPubKey，它规定将来花这一项时要满足的条件。示例交易 B:0 的 22 字节为 `00 14 06afd46bcdfd22ef94ac122aa11f241244a37ecc`。节点识别版本 0 和 20 字节见证程序，按 P2WPKH 规则验证后续花费。

**现在收款。** Bob 的钱包已从自己的描述符派生一批脚本并建立查找索引。B 到达时，钱包依次用输出的完整脚本字节查表。B:0 命中，于是登记 (B 的 txid, 0)、60,000 聪和所在交易状态；B:1 的脚本属于 Alice。观察钱包也能做这种匹配。匹配说明输出在钱包的跟踪范围内；能否独立花费，还要看能否满足脚本要求、获得签名。

**以后花费。** Bob 要花 B:0 时，在新交易的输入里引用这个 outpoint 并提供相应见证。全节点读取旧输出的真实脚本和金额，检查公钥哈希与签名，并核对输出在当前状态下仍可花。它无需访问 Bob 的钱包脚本索引。

| 正在做的事 | 读取的条件 | 谁提供见证 |
|---|---|---|
| Alice 用 B 花旧输出 U | U 的 scriptPubKey 内的 Alice 公钥哈希 | Alice 在 B 的输入 0 提供 |
| B 给 Bob 创造 B:0 | B:0 写入 `00 14 06afd4…7ecc` | Bob 收钱时无需签名 |
| Bob 以后用另一笔交易花 B:0 | B:0 已写入的 Bob 公钥哈希 | Bob 在那一笔新交易的对应输入提供 |

## 见证是一种怎样的数据结构？

在交易对象里，每个输入可有一份 witness，它是**有顺序的字节串列表**。在有见证交易的线格式里，各输入的列表依输入顺序统一写在所有输出之后、locktime 之前。每个列表先写元素数，每项先写字节长度，数量与长度都用 CompactSize。没有见证的那个输入在这种格式下占一个 `00` 空列表。若整笔交易都没有见证，则使用基本格式，省去整段见证以及 marker、flag。

原生 P2WPKH 的 scriptSig 必须为空，见证恰有两项。第一项是 DER 编码的 ECDSA 签名再附一字节签名模式（本例 `01 = SIGHASH_ALL`）。第二项为公钥，本课使用 33 字节压缩公钥。可以把 B 的输入画成 `[Alice 的签名及模式, Alice 的公钥]`。具体签名长度依实际 DER 编码而定。见证中的每项是数据，计数与长度也只负责解码。

## 节点如何检查？

节点按输入的 outpoint 取到 U 的金额和脚本。发现 v0 的 20 字节程序后，以见证两项初始化执行栈，按与 P2PKH 相应的脚本执行。下表中栈顶在右，H 是 U 原先承诺的 20 字节。

| 指令 | 执行后栈的含义 |
|---|---|
| 初始 | 签名，公钥 |
| OP_DUP | 签名，公钥，公钥副本 |
| OP_HASH160 | 签名，公钥，刚算出的 20 字节 |
| 推入 H，再 OP_EQUALVERIFY | 两份哈希相同则继续，留下签名、公钥。不同则失败 |
| OP_CHECKSIG | 读取签名模式，按 BIP143 和 U 的金额等字段重算摘要，验签后压入结果 |

对于此见证花费，最终栈须恰有一个真值。填写新收款脚本、构造签名用的 scriptCode、运行验签检查发生在不同环节。以 B 为例，前者可写 Bob 的哈希，后两者针对正在花的 U。验块时有任何输入的必需脚本检查失败，整块无效。

U 的脚本承诺 Alice 的公钥哈希。Bob 的公钥能用于花费 B:0；用它验证 U 的花费会在公钥哈希检查处失败。

**英文术语**　P2PKH（Pay to Public Key Hash，支付到公钥哈希）、ECDSA（Elliptic Curve Digital Signature Algorithm，椭圆曲线数字签名算法）、DER（Distinguished Encoding Rules，可辨别编码规则）、txid（transaction identifier，交易标识）、BIP（Bitcoin Improvement Proposal，比特币改进提案）。
