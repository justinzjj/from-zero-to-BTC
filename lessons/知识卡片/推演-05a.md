# 拆读见证的长度、次序与字节

对一笔带见证的交易，每个输入都对应一份见证。把其中一份想成一个有次序的列表，每一项可以装一串不同长度的字节。对于 B 唯一的输入，Alice 的钱包写入两项；节点验证的是她能否满足旧输出 U 的花费条件。

| 输入 0 的见证 | 谁写、谁读 |
|---|---|
| 第 0 项：DER 编码的 ECDSA 签名，末尾附一字节 01 | Alice 签名时写；验证者读取 01，据此按 SIGHASH_ALL 计算摘要，再验证签名 |
| 第 1 项：Alice 的 33 字节压缩公钥 | Alice 写；验证者以 HASH160 和 U 里的 20 字节哈希比对，并用公钥验签 |

**跟着字节读。** 在带见证序列化里，先读完所有输入与输出，再按输入顺序读各自的见证，最后读锁定时间。每份见证先写元素个数，每个元素再写长度和内容，两个计数都用 CompactSize。示例交易 B 的结构可读作「02｜签名项长度｜签名及 01｜21｜公钥」。这里 21 是十六进制的 33；签名项的精确长度取决于实际签名字节。这一段是结构示意。卡 06 给出完整官方样例，可逐字节数。

**什么时候轮到 Bob？** B 当下写入 Bob 的是输出 B:0 的花费条件。将来 Bob 再花 B:0 时，会在下一笔交易对应输入里写自己的见证。因此 Bob 收书款时不需要给 Alice 回传签名。

见证列表中的顺序有协议含义。P2WPKH 按位置读取签名与公钥，颠倒次序会导致验证失败。

**英文术语**　P2WPKH（Pay to Witness Public Key Hash，支付到见证公钥哈希）、ECDSA（Elliptic Curve Digital Signature Algorithm，椭圆曲线数字签名算法）、DER（Distinguished Encoding Rules，可辨别编码规则）。

**规范与实现**　[BIP141 的 Transaction ID 与 Witness program 两节](https://bips.dev/141/#transaction-id) · [Bitcoin Core v29.0 的 CScriptWitness 定义](https://github.com/bitcoin/bitcoin/blob/v29.0/src/script/script.h#L541-L545)
