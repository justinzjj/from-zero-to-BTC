# 计算到期高度并对照激活条件

矿工填写块头时间，节点依据父链和本地时间分别检查。时间锁则约束一笔交易最早能在哪个块出现。

**先读三个数。** 候选块 K 有高度 H、有矿工自报时间；K 的父块 P 另有 MTP，即 P 和之前最多十个祖先的块头时间排序后取中位数。主网要求 K 的时间严格大于 P 的 MTP。Core v29.0 遇到超过节点当前时间两小时的头会暂不接受，待时间推进可重新检查。矿工写 K 的时间，无法单靠这个字段把本块交易的时间锁拨快。

| 约束 | 写在哪里 | 节点怎样核对 |
|---|---|---|
| 绝对时间锁 | 交易末尾的 nLockTime | 0 表示没有该锁。小于 500,000,000 的正值按高度解释，其余按 Unix 秒数。至少一个输入的 nSequence 不是 0xffffffff 时，需要锁值严格小于候选块高度或父块的 MTP。全体输入均为最终序号时，交易级绝对锁不起作用。 |
| 相对时间锁 | 每个输入自己的 nSequence | 对版本 ≥ 2 且第 31 位为 0 的输入，低 16 位给出等待量。第 22 位为 0 时按块数等待，为 1 时每单位为 512 秒。按时间时，从创建输出所在块的前一块的 MTP 起，算到候选块父块的 MTP。 |
| CLTV、CSV | 收款方可把操作码放入锁定条件，例如 P2WSH 所承诺的脚本 | CLTV 要求花费交易采用匹配类型且足够大的 nLockTime，当前输入不能为最终序号。常用 CSV 条件把同类型的相对下限加到该输入，验证版本、启用位及数值。最终能否进当前块，仍要核对上面两类交易规则。 |

例如 U 创建于高度 900,000，花费它的 B 版本为 2，nSequence 为 3，nLockTime 为 0。高度差至少为 3，因此首次满足相对高度锁的候选块高度是 900,003。

**为什么旧节点和新节点会表现不同？** 软分叉在激活后收紧有效块集合。升级节点开始拒绝违反新条件的块；只认识旧规则的节点仍可把符合新规则的块当作有效。BIP 9 给出一种历史部署方法：节点按预设周期核对版本位信号，达到条件进入锁定期，之后进入 ACTIVE 才执行新规则；超时可进入 FAILED。信号用于协调部署。实施验证仍靠各节点自己的软件，具体激活方式与参数须看该次升级。BIP 68、112、113 曾联动部署。

**英文术语**　P2WSH（Pay to Witness Script Hash，支付到见证脚本哈希）、MTP（Median Time Past，过去区块时间中位数）、CLTV（Check Lock Time Verify，对应 OP_CHECKLOCKTIMEVERIFY）、CSV（Check Sequence Verify，对应 OP_CHECKSEQUENCEVERIFY）、BIP（Bitcoin Improvement Proposal，比特币改进提案）。
