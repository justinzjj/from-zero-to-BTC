01 · 哈希函数、原始字节与交易标识

哈希函数把任意长度的字节串映射成固定长度的摘要。同一种算法处理完全相同的字节，总会得到同一个结果。十六进制只是字节的书写方式。SHA-256 输出 32 字节，RIPEMD-160 输出 20 字节。双 SHA-256 把第一次的 32 个原始字节再哈希一次；HASH160 把 SHA-256 的结果交给 RIPEMD-160。

交易需要一个任何节点都能独立计算的名字。txid 用不含见证的基本序列化计算双 SHA-256，wtxid 用含见证的完整序列化计算。没有见证时两者相同。引用输出用 txid 和输出序号；按浏览器显示值对照原始字节时还要认清字节顺序。

字节序。 字节序描述多字节数值的排列顺序。节点哈希的是协议规定的字节串。常见工具显示 txid 时，使用与交易输入中前序哈希字段相反的字节顺序；核对时要先统一表示。

输入与输出。 用三个原始字节 61 62 63 计算 SHA-256，结果是 ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad。计算 txid 时换成交易的基本序列化字节，先取 SHA-256，再对所得的 32 字节取 SHA-256，最后反转摘要的字节顺序得到常用显示值。

02 · 私钥、公钥与压缩公钥

secp256k1 是 SEC 2（Standards for Efficient Cryptography 2）规定的曲线名称。在这条曲线上，私钥是从 1 到 n−1 的整数 d，n 是基点 G 的阶。公钥是曲线上的点 Q = dG。压缩公钥用 33 个字节表示同一个点：首字节 02 或 03 标明 y 的奇偶性，其余 32 字节保存 x 坐标。

这种对应关系把授权与核验分开。控制私钥的人可以签名，别人拿公钥即可验签；从公钥逆推出随机私钥在实践中不可行。压缩编码让钱包和节点用更少字节传递同一个点。

编码一把公钥。 取公开演算值 d = 2，则 Q = G + G。在有限域中倍点，斜率为 3x²/(2y)，新横坐标为斜率² − 2x，新纵坐标为斜率 × (x − 新横坐标) − y，各步模 p。此点的 y 为偶数，因此编码为 02c6047f9441ed7d6d3045406e95c07cd85c778e4b8cef3ca7abac09b95c709ee5。首字节之后的 32 字节就是横坐标。

03 · 分层确定性钱包与扩展密钥

分层确定性钱包（HD 钱包）用一份种子建立一棵密钥树。BIP32 的每个树节点都有密钥与链码；两者合在一起构成派生下一层所需的核心材料。一条路径记录从根到这个位置所经过的子编号。采用 BIP39 的钱包可用助记词和可选口令得到种子。

钱包可以为不同付款给出不同的收款地址，并从同一根材料重建这些密钥。收款和找零可以各用一个分支。普通派生允许观察钱包用扩展公钥生成子公钥；硬化派生需要父级私钥材料。恢复时还要知道钱包采用的派生路径和脚本类型。

种子与密钥的区别。 种子是生成根节点的起点。BIP32 从种子计算出主私钥和主链码。一个普通私钥足以算出自己的公钥，扩展私钥还包含继续派生所需的链码。Bech32 地址则来自某个子公钥对应的收款条件，是可以交给付款人的信息。

一层普通子私钥如何计算。 输入父私钥 k、32 字节父链码 c、4 字节大端下标 i。计算 HMAC-SHA512(key=c, data=压缩父公钥 || i)，将 64 字节结果切为左右两半 L、R。左半按大端解释为整数；在有效情形，子私钥等于 (L + k) mod n，子链码等于 R。硬化派生将消息前段换成 00 || 32字节父私钥，下标从 2³¹ 起。L ≥ n 或所得子私钥为零时须改用下一下标。扩展密钥的序列化共有 78 字节，依次为版本 4、深度 1、父指纹 4、子编号 4、链码 32、密钥数据 33。

04 · 收款地址、见证程序与输出脚本

输出脚本（scriptPubKey）是一项交易输出携带的花费条件。以原生 P2WPKH 为例，脚本由版本 0 和一个 20 字节的公钥哈希组成，这 20 字节称为见证程序。Bech32 是编码格式的名称。Bech32 地址将网络、版本和程序编码为带校验和的文字。找零脚本是付款钱包为自己控制的剩余金额准备的输出脚本。

收款人需要把花费条件可靠地交给付款人。地址便于展示、扫码和检查常见录入错误；付款钱包解码后，把准确的脚本字节和金额写进交易。全节点日后可按这个条件验证花费。

实际脚本。 Bob 的收款公钥做 HASH160 后得到 06afd46bcdfd22ef94ac122aa11f241244a37ecc。前置版本 0 的操作码 00 和压入 20 字节的指令 14 即是输出脚本。编码地址时，将这 20 字节从 8 位组转换为 5 位组，前置见证版本，配上主网前缀 bc 和 6 个 Bech32 校验字符，得到 bc1qq6hag67dl53wl99vzg42z8eyzfz2xlkvxechjp。

英文术语　P2WPKH（Pay to Witness Public Key Hash，支付到见证公钥哈希）、BIP（Bitcoin Improvement Proposal，比特币改进提案）。

05 · P2WPKH 与脚本执行

Bitcoin Script 用操作码和数据表达并检验花费条件。P2WPKH（Pay to Witness Public Key Hash）是一种见证版本 0 的输出类型，它在输出脚本中给出一个 20 字节公钥哈希。花费原生 P2WPKH 时，输入的 scriptSig 为空，见证携带签名和公钥。

这里缓存的是输出脚本（scriptPubKey），即交易输出中规定将来怎样花这笔钱的字节。Bob 的钱包用 B:0 的完整脚本查索引，命中就能识别书款；将来花费时，再从对应派生位置查找密钥或签名器。以后花费时，节点核对公钥哈希并验证签名，由此判断这次花费是否得到授权。识别脚本和实际签署花费可以由不同设备负责。

从栈到判定。 节点从旧输出读出 00 14 <20字节哈希>，要求输入的见证恰有签名和公钥两项。执行相当于 OP_DUP OP_HASH160 <20字节哈希> OP_EQUALVERIFY OP_CHECKSIG 的检查：复制栈顶公钥、求其哈希、与旧输出承诺比较，最后用公钥检查针对本次花费的签名。任何必需检查失败都无法花费该输出。

05a · 输入见证的数据结构

见证（witness）是供节点核验花费条件的数据。每个输入对应的有序字节串列表称为见证栈（witness stack）。输入决定它要花哪个旧输出，旧输出的脚本决定见证需要提供哪些数据。对于原生 P2WPKH，列表第一项是附签名模式字节的签名，第二项是公钥。

验证者需要拿到满足旧输出条件的材料。把这些材料独立编码后，节点可以验证花费，并分别计算基本交易标识 txid 和覆盖见证的 wtxid。交易的输入输出关系依然可以用基本交易标识引用。

列表怎样编码。 每个输入先写见证项数，再按顺序写每项的字节长度和内容。项数、长度都是 CompactSize。P2WPKH 两项中的签名证明授权，公钥用于验签并与旧输出的公钥哈希比对。

Core 表示与线路格式。 Bitcoin Core v29.0 的 CScriptWitness::stack 是 std::vector<std::vector<unsigned char>>。外层下标选中一项，内层存该项的原始字节。公开 BIP143 向量中的一个输入编码为 02 | 47 | 70字节DER签名及1字节模式 | 21 | 33字节公钥；02、47、21 均为十六进制。

06 · UTXO 记账模型：输出、输入与未花费集合

**UTXO（Unspent Transaction Output，未花费交易输出）**是一笔已有交易创建、截至所观察的链尖仍未被消费的输出。它有一个可被下一笔交易引用的位置、一笔整数金额，以及一段规定花费条件的脚本。Bitcoin Core v29.0 用下面两个对象表达这项记录：用 COutPoint 查哪一项，用 Coin 保存查到的内容。

所属对象 Core 字段与类型 含义
查找键 COutPoint hash: Txid 创建该输出的交易标识（transaction identifier，txid），32 字节
查找键 COutPoint n: uint32_t 该交易输出数组中从 0 开始的下标
记录 Coin → out: CTxOut out.nValue: CAmount 有符号 64 位整数，以聪为单位；有效输出的金额须在共识允许范围内
记录 Coin → out: CTxOut out.scriptPubKey: CScript 可变长脚本字节，规定花费这项钱要满足的条件
记录 Coin fCoinBase: unsigned int（1 位） 创建它的交易是否为 coinbase，花费时用于检查成熟期
记录 Coin nHeight: uint32_t（31 位） 创建输出的区块高度，也用于成熟期和相对时间锁检查

前两个字段来自引用位置。中间两个字段来自原交易输出。最后两个字段由节点处理所在区块时补上。后来花费它的交易只需在输入的 prevout 写出同一对键，节点即可取得金额和脚本进行验证。交易类型定义 · Coin 定义

07｜钱包从哪些旧输出凑出书款？

选币发生在签名前，由 Alice 的钱包做决定。Bob 的节点检查交易是否有效，无须重走 Alice 的选币算法。

钱包列出能花的旧输出，逐个读取金额、锁定脚本、确认情况及本地锁定状态。每增加一个输入，交易通常会变大。钱包因此可按“面值减去花此输入所需费用”的有效价值来比较候选项。找零还要考虑现在新建一个输出以及以后花掉它的成本。

**Branch and Bound（分支限界搜索）**会尝试“选这个、跳过这个”两种分支，寻找能付清目标且多出金额不超过找零成本的组合，争取省去找零输出。若当前组合已经太多，或把余下候选都加上也不够，这条路就可以提前结束。例：有效价值为 6、4、3，目标为 7，容许多付 0。选 6 后再选 4 会超额，退回后尝试 4 加 3，恰好付款。实际 Core 以输出组为候选，设搜索次数上限，并会比较其他策略。示例交易 B 已给定一个输入和两个输出，不能据此断言 B 是这个算法选出来的。

把费用落到账上。 B 花掉 U 的 100,000 聪，输出 60,000 和 39,000 聪。输入总额减输出总额得到 1,000 聪手续费。按字节计算费率时，先取去见证序列化大小 S 和完整序列化大小 T，重量为 3S + T（WU），虚拟大小为重量除以 4 并向上取整。若两份大小为 113 和 223 字节，则重量为 562 WU、虚拟大小为 141 vB，1,000 聪相当于约 7.09 聪/vB。这组长度是示范条件；B 的签名字节未给全，不能从金额推出实际大小。

选币时，用输入总额减去付款和预计费用得到找零。例如 100,000 − 60,000 − 1,200 = 38,800 聪。

英文术语　vB（virtual byte，虚拟字节）、WU（weight unit，重量单位）。

08 · BIP143 签名摘要与 SIGHASH_ALL

签名摘要是从本次花费指定字段计算出的 32 字节值。BIP143 定义了见证版本 0 签名时的字段顺序与哈希算法。scriptCode 表达本输入使用的脚本条件，另一个字段给出正在花费的旧输出金额。SIGHASH_ALL 是 Bitcoin 的签名哈希类型（signature hash type）常量，值为 0x01，覆盖全部新输出。

签名者与验证者需要从同一交易重建完全一致的消息。规定字节编码和签名范围后，收款金额或收款脚本一旦被改动，原先覆盖它们的签名便无法通过检查。

普通 SIGHASH_ALL 的序列化顺序。 对见证版本 0 且未设 ANYONECANPAY 的输入，依次拼接版本、hashPrevouts、hashSequence、当前 outpoint、带长度的 scriptCode、旧输出金额（8 字节小端）、当前 sequence、hashOutputs、锁定时间和签名模式（4 字节小端）。三个中间哈希分别由所有输入引用、所有输入序号、所有序列化新输出做双 SHA-256 得到；最后对整串再做双 SHA-256。本例模式在摘要末尾编码为 01000000，在见证签名之后编码为 01。

英文术语　P2WPKH（Pay to Witness Public Key Hash，支付到见证公钥哈希）、SHA-256（Secure Hash Algorithm 256-bit）、BIP（Bitcoin Improvement Proposal，比特币改进提案）。

09 · ECDSA 签名、验证与 DER 编码

ECDSA 是一种公钥数字签名算法。签名端用私钥、消息摘要和一次性标量 k 得到两个整数 r 和 s。验证端用公钥、同一摘要以及 r、s 检查签名。DER 规定这对整数如何编码成字节。

付款人需要授权一笔指定的花费，同时让任意节点独立核验。P2WPKH 将 DER 签名附上签名模式字节，并把它与公钥装入见证；私钥只在签名端使用。

签名与验签的计算。 设基点为 G、阶为 n，私钥 d 的公钥为 Q = dG，摘要解释为整数 z。签名端计算 R = kG，取 r = x(R) mod n，再求 s = k⁻¹(z + rd) mod n，r 或 s 为零须重选 k。验签端先检查 r、s 的范围，再算 w = s⁻¹ mod n 和点 X = (zw mod n)G + (rw mod n)Q。X 不是无穷远点且 x(X) mod n = r 时通过。

10 · P2P 网络与交易中继

P2P（点对点）是一种网络组织方式。一个节点维持若干邻居连接，每条连接的两端都可以收发协议消息。交易中继是其中一项工作：节点通告交易标识，缺数据的邻居请求交易，然后按自己的规则检查。

一条通告的数据。 库存项由 4 字节类型和 32 字节哈希组成。节点收到 inv 后，若缺少该对象，就选通告过它的邻居，用 getdata 指定所需项。对方回 tx 消息，节点解析交易、检查后再决定是否中继。支持 BIP339 并协商成功时，可以用 wtxid 标识待取交易。

12 · Merkle 树、树根与包含证明

Merkle 树将一组有序数据的哈希逐层配对，拼接并哈希，最终得到一个根。Bitcoin 的普通交易树以块内交易的 txid 为叶，根写入区块头。包含证明由目标叶的位置和沿途各层的兄弟哈希组成。

一个区块头需要承诺整块的交易次序和内容。持有区块头的人可以用一条短路径核对某笔交易是否被包含。证明的范围限于包含关系；脚本和输入有效性仍需交易与链状态。含见证的区块还通过 coinbase 承诺另一棵见证树。

简化支付验证（SPV）。 轻客户端可以保存和核验区块头，用包含证明确认某笔交易被某个头承诺，再观察这条头链的累计工作量。这个判断依赖客户端获得的链和相应的算力假设。

三片叶子的计算。 令 D 表示双 SHA-256，a、b、c 表示按块内次序排列的 32 字节交易哈希。末层为奇数时复制 c，先算 p = D(a || b)、q = D(c || c)，再算根 D(p || q)。证明 b 的包含关系只需提供左兄弟 a、右兄弟 q 及方向。哈希函数的输入是字节拼接。

14 · 工作量证明、网络目标与 nBits

工作量证明（Proof of Work，PoW）在 Bitcoin 中要求一个 80 字节区块头的双 SHA-256 哈希按整数解释后小于等于目标 T。nBits 是区块头里对目标的紧凑编码；nonce 是矿工可以改变的一个 4 字节字段。T 越小，随机一次尝试达标的概率越低。

所有节点都能用很少的计算核对一个达标结果；产生结果通常需要大量尝试。每个有效块按其目标贡献可计算的工作量，节点据此比较有效分支。主网按既定周期调整目标，使长期平均出块间隔趋近十分钟。

目标与累计工作量。 给定 T，一次均匀哈希命中的概率是 (T + 1) / 2²⁵⁶。节点按目标为每个有效块计入工作量，再沿父块相加。同一目标下，偶然找到更小的哈希不会多得工作量。

80 字节头的布局。 按字节偏移依次是版本 [0,4)、父块哈希 [4,36)、Merkle 根 [36,68)、时间 [68,72)、nBits [72,76)、nonce [76,80)。对合法例值 0x1d00ffff，指数为 0x1d，系数为 0xffff，解得 T = 65535 × 256²⁶。节点对序列化头做双 SHA-256，以小端读出结果整数 h，核对 h ≤ T，并核对 nBits 符合父链规定。

英文术语　SHA-256（Secure Hash Algorithm 256-bit）。

L2 有效地延长 L1，且该支累计工作领先 Bob 找到最近共同祖先 P，断开 K，恢复 U，移除 B 的两个输出。依次接入 L1、L2，C 花掉 U。钱包保留 B 的交易记录，并把它标为冲突，60,000 聪退出已确认余额。 在 L1 上接 L2。两个节点得到同一活动链。

「最长链」怎样量？ 单块工作量为 floor(2²⁵⁶ / (T+1))，体现该目标下找出一个合格哈希通常有多难。对同一个 T，运气特别好、找到更小哈希的矿工所得工作量也相同。区块索引累加父块工作量和本块工作量，得到 nChainWork。本例假设各块同一难度，一块对两块时，后者多一块的工作量。跨难度时期要逐块相加。可用第 14 卡创世块的真实目标复算：Python 表达式 (1 << 256) // ((0xffff << 208) + 1) 给出 4,295,032,833。

平手时谁先？ Core v29.0 在普通运行中用本地序号等信息给同工作量的候选排序，通常有利于较早取得完整数据的分支。收到区块头的时刻、区块的自报时间戳、任一观察者看到的先后，都无法建立全网统一的“第一名”。若 L2 比 L1 的块体先到，Bob 需要取得缺失的祖先数据、验证父链，才能把这个分支接为活动链。

无效祖先上的后继工作量无法使该分支有效。节点只在符合共识的分支之间比较累计工作量。

17　Bob 断开一个块时，怎样找回已经花掉的 U？

断开 K 需要两份互补的数据：从 K 的交易读出该移除哪些新输出，从撤销记录读出先前被花掉的旧币内容。

逆序移除按块内交易顺序从后往前撤销。若 B 创建了 B:0，而同块后面的 D 花掉 B:0，断块时先撤销 D，移除 D 的输出并恢复 B:0；再撤销 B，移除 B:0、B:1 并恢复 U。这样 B:0 在断块完成后不会残留。

在 Bob 的钱包里，「断开旧块」意味着什么？

设 K 是 Bob 当前链尖，父块是 P。K 确认了 B，Bob 因而看到一笔已确认的 60,000 聪。后来节点发现从 P 分出的另一条有效分支累计工作量更大。切换时先从旧链尖往回走：断开 K，撤回 K 创建的输出，凭撤销记录恢复 K 花掉的旧输出 U。K 可以继续存在于本地块文件和区块索引中。钱包收到断块事件后撤下 B 的旧确认位置，保留原交易记录。

下一步才连接新分支。如果其中 C 花了 U，B 与它冲突；如果新分支也含 B，B 可以在新位置重新获得确认；如果两者都没被收录，B 能否重新入池须再检查输入和本地策略。停在「断开」这一步，还不能断定钱已经退给 Alice，或 Bob 永远收不到书款。

18 · 时间锁、链上时间与规则激活

时间锁规定一笔交易最早何时可以被区块收录。绝对锁以高度或时间设门槛，相对锁从输入所引用输出的链上位置起算。MTP 是一段近期区块头时间戳的中位数，为共识检查提供可重复计算的时间参照。

交易双方可以约定“到期后才能花”或“收到后再等一段时间”，每个验证节点都能独立判断是否到期。这些规则也有生效边界：软分叉收紧有效块条件，激活机制确定升级节点从什么时候开始执行新增规则。

锁的刻度。 绝对锁由 nLockTime 表达，可设为区块高度或时间。相对锁由输入的 nSequence 表达，可按块数或 512 秒为单位等待。CLTV 和 CSV 是脚本操作码，分别要求花费交易采用满足脚本下限的绝对锁或相对锁。

如何从输入字段读取相对锁。 对版本至少为 2 的交易，32 位 nSequence 的第 31 位清零才启用 BIP68；低 16 位是等待量，第 22 位选择按区块或按 512 秒计时。值 0x00000003 表示至少相隔 3 个高度，0x00400003 表示按规定的两端 MTP 至少相隔 1,536 秒。父块 MTP 取父块及其之前最多十个祖先的时间戳，排序后取中间值。

19 · 聪与 BTC 的计量关系

20 · 钱包与全节点的职责

钱包管理本用户能识别的脚本、密钥或签名器，以及相关交易记录。全节点从区块与交易独立验证规则，维护自己采用的链及其未花费输出集合。两者可以运行在同一台设备上，也可以分开部署。

用户需要查询与自己有关的钱、构造并授权付款；网络参与者需要判断付款是否符合规则。钱包把人的意图变成交易，并把节点观察到的事件变成余额与确认数。全节点提供独立验证所依据的状态。

21 · 为什么有人愿意花电挖这个块？

矿工投入设备、电力和时间，争取让自己构造的有效块进入活动链。块首的特殊交易叫 coinbase，构造者可以在它的输出中指定收款条件，最多领取该高度的区块补贴加本块全部手续费。只有补贴来自新发行；手续费来自已有输出。

跟着 1,000 聪走。 B 引用 100,000 聪，产生 60,000 和 39,000 两个输出。K 如果选 B，可领取金额就由它增加 1,000 聪。为方便心算，假设示例区块 K 高度为 840,001，且仅有 coinbase 与 B。这是设定的高度，不对应那一高度的主网块。此时已经过四次减半，补贴为 50 ÷ 16 = 3.125 BTC = 312,500,000 聪，所以 coinbase 的输出总额最多为 312,501,000 聪。高度为 H 的 coinbase 输出最早能由高度 H+100 的块内交易花费。

谁会付，谁会查。 构造者自己写 coinbase，各全节点按高度、块内交易和各输入的旧金额独立算上限。矿场交回一个普通份额时，只由矿池按双方约定记工和结算。Bob 转发交易或验证别人的块，协议没有给他另设报酬。若另一个有效分支后来胜出，旧分支的 coinbase 输出也从活动链状态退出。这样，矿工争取的是能被别人验证并继续延伸的块；奖励是经济动机，不能保证每个参与者必然诚实。

本例允许少领奖励；超领 1 聪就会使整块无效。

复算两种交易标识

Alice 提交的是有确定顺序的一串交易字节。两台机器只要取相同的字节、用相同的算法，就会算出相同的标识。

先摸到字节。 十六进制的两个字符写一个字节。把字符串 abc 编成 ASCII 得到三个字节 61 62 63。把屏幕上看到的六个字符 616263 逐字编码，会得到另一份输入。SHA-256 把任意长度的字节串映射成 32 字节。双 SHA-256 把第一次的 32 个原始字节再送入 SHA-256。RIPEMD-160 输出 20 字节。钱包给压缩公钥做 HASH160 时，先算 SHA-256，再把 32 字节交给 RIPEMD-160。

from hashlib import sha256
raw = bytes.fromhex("61 62 63")
first = sha256(raw).digest()
print(first.hex())
print(sha256(first).hexdigest())

第一行应以 ba7816bf8f01cfea 开头，第二行为 4f8b42c22dd3729b519ba6f68d2da7cc5b2d606d05daed5ad5128cc03e6c6358。

想标记什么 双 SHA-256 的输入 谁会用
txid 基本格式的版本、输入、输出、锁定时间 Bob 以后花 B:0 时，用它和编号 0 定位旧输出
wtxid 含见证时，把标记、标志、各输入见证也按规定位置编码 支持见证交易通告的节点可用它识别完整版本，区块见证承诺也使用它，coinbase 叶另有约定

两种 ID 在浏览器和 RPC 中通常都按摘要反转字节顺序后显示。比如摘要的示意尾部为 … ab cd，显示就以 cdab… 开头。对没有见证的交易，两种计算使用同一份基本格式。签名时要算的 BIP143 摘要另有字段排列，见专题 08。

txid 只覆盖基本交易字段。见证签名的字节变化会影响 wtxid；即使签名无效，仍可按序列化字节计算两种标识。

用公开小整数演算公钥

收款钱包先取得一个私钥整数 d，或从已有的扩展公钥派生相应公钥。给定私钥时，用 secp256k1 规定的基点 G 做标量乘法，得到唯一公钥点 Q。将来花 B:0 时，Bob 才用相应私钥签名。

手算一个和 B:0 对得上的例子。 曲线上每个点有 x、y 两个坐标，满足 y² ≡ x³ + 7 (mod p)，其中 p = 2²⁵⁶ − 2³² − 977。加减乘除都在这个有限集合中算，除法用模逆。合法私钥的范围为 1 到 n−1，n 是基点 G 的阶（把 G 相加 n 次会得到群的单位元）。真实钱包从安全随机数或安全生成的种子派生密钥。下面的 d=2 是公开的演算参数，任何人都能为这把钥匙签名。

p = 2**256 - 2**32 - 977
x = 0x79be667ef9dcbbac55a06295ce870b07029bfcdb2dce28d959f2815b16f81798
y = 0x483ada7726a3c4655da4fbfc0e1108a8fd17b448a68554199c47d08ffb10d4b8
slope = 3*x*x * pow(2*y, -1, p) % p
qx = (slope**2 - 2*x) % p
qy = (slope*(x-qx) - y) % p
pub = bytes([2 + qy % 2]) + qx.to_bytes(32, "big")
print(pub.hex())

这里算的是 2G，即 G 与自己相加。一般的标量可以按二进制位用倍点与加点得到 dG。将点压缩时，取前缀 02 表示偶数 y，03 表示奇数 y，再跟 32 字节大端 x。由 x 代回曲线方程和这个奇偶位就能恢复对应的 y。上例的 33 字节结果为 02c6047f9441ed7d6d3045406e95c07cd85c778e4b8cef3ca7abac09b95c709ee5。用该公钥的 HASH160 可以构造 Bob 的收款脚本。公开该点让别人可以验签，从一般安全随机生成的公钥反求私钥在计算上不可行。

压缩前缀 02 与 03 选取同一横坐标上不同的曲线点，编码出的公钥及其 HASH160 也随之不同。

从助记词到 Bob 展示的收款地址

在采用 BIP39 的钱包里，初始化一次就能为后续收款准备一棵密钥树。以 12 词为例，钱包产生 128 位随机数，附上 SHA-256 摘要开头 4 位校验，再每 11 位查一次 2,048 词的词表。恢复时，以规范化（UTF-8 NFKD）的词句为密码，以同样规范化的 mnemonic 加可选口令为盐，用 PBKDF2-HMAC-SHA512 迭代 2,048 次得到 64 字节种子。之后由 BIP32 得到主私钥和链码，再逐层派生。一个普通子私钥可用于计算自己的公钥和地址；要重建整棵树，还需要种子或相应的根扩展密钥。不同钱包采用的备份形式可以不同，Core 描述符钱包也可从描述符跟踪脚本。

取一个子私钥 d，算公钥点 dG，将压缩公钥做 HASH160 得到 20 字节。收款脚本是 00 14 <这20字节>；主网地址把见证版本 0、这 20 字节和网络前缀 bc 按 Bech32 编码。Alice 扫码时反向解码，还原 Bob 交给她的花费条件。给出地址这一步可以在收到付款以前完成。

Bob 把收款条件编码成便于抄写或扫码的地址。Alice 的钱包解码它，再把金额与相应的锁定脚本写入交易。

为什么 Alice 还给自己写一个找零脚本？

U 必须整项花费。Alice 交出 100,000 聪，付书款 60,000 聪，留 1,000 聪作手续费，还剩 39,000 聪。她的钱包在自己的内部派生分支取一个新公钥，按与收款相同的规则生成脚本，将 39,000 聪和该脚本写入 B:1。这个脚本规定谁可以花 B:1。Alice 的钱包知道它来自自己的派生分支，因此将它识别为找零；验证节点只看见一个普通输出。B:0 与 B:1 都可以使用 P2WPKH，输出顺序本身不能证明哪项是找零。

逐步执行脚本并检查归属

P2WPKH 的全称是 Pay to Witness Public Key Hash。创建输出时，付款钱包留下一个公钥哈希。后来有人花这项输出，节点才检查公钥和签名。

脚本怎样让钱包认出「这项输出与我有关」？

脚本是按 Bitcoin Script 规则解释的一串字节。操作码描述动作，紧随压栈指令的字节可以携带数据。每个交易输出都有金额和 scriptPubKey，它规定将来花这一项时要满足的条件。示例交易 B:0 的 22 字节为 00 14 06afd46bcdfd22ef94ac122aa11f241244a37ecc。节点识别版本 0 和 20 字节见证程序，按 P2WPKH 规则验证后续花费。

现在收款。 Bob 的钱包已从自己的描述符派生一批脚本并建立查找索引。B 到达时，钱包依次用输出的完整脚本字节查表。B:0 命中，于是登记 (B 的 txid, 0)、60,000 聪和所在交易状态；B:1 的脚本属于 Alice。观察钱包也能做这种匹配。匹配说明输出在钱包的跟踪范围内；能否独立花费，还要看能否满足脚本要求、获得签名。

以后花费。 Bob 要花 B:0 时，在新交易的输入里引用这个 outpoint 并提供相应见证。全节点读取旧输出的真实脚本和金额，检查公钥哈希与签名，并核对输出在当前状态下仍可花。它无需访问 Bob 的钱包脚本索引。

见证是一种怎样的数据结构？

在交易对象里，每个输入可有一份 witness，它是有顺序的字节串列表。在有见证交易的线格式里，各输入的列表依输入顺序统一写在所有输出之后、locktime 之前。每个列表先写元素数，每项先写字节长度，数量与长度都用 CompactSize。没有见证的那个输入在这种格式下占一个 00 空列表。若整笔交易都没有见证，则使用基本格式，省去整段见证以及 marker、flag。

原生 P2WPKH 的 scriptSig 必须为空，见证恰有两项。第一项是 DER 编码的 ECDSA 签名再附一字节签名模式（本例 01 = SIGHASH_ALL）。第二项为公钥，本课使用 33 字节压缩公钥。可以把 B 的输入画成 [Alice 的签名及模式, Alice 的公钥]。具体签名长度依实际 DER 编码而定。见证中的每项是数据，计数与长度也只负责解码。

节点如何检查？

节点按输入的 outpoint 取到 U 的金额和脚本。发现 v0 的 20 字节程序后，以见证两项初始化执行栈，按与 P2PKH 相应的脚本执行。下表中栈顶在右，H 是 U 原先承诺的 20 字节。

拆读见证的长度、次序与字节

对一笔带见证的交易，每个输入都对应一份见证。把其中一份想成一个有次序的列表，每一项可以装一串不同长度的字节。对于 B 唯一的输入，Alice 的钱包写入两项；节点验证的是她能否满足旧输出 U 的花费条件。

输入 0 的见证 谁写、谁读
第 0 项：DER 编码的 ECDSA 签名，末尾附一字节 01 Alice 签名时写；验证者读取 01，据此按 SIGHASH_ALL 计算摘要，再验证签名
第 1 项：Alice 的 33 字节压缩公钥 Alice 写；验证者以 HASH160 和 U 里的 20 字节哈希比对，并用公钥验签

跟着字节读。 在带见证序列化里，先读完所有输入与输出，再按输入顺序读各自的见证，最后读锁定时间。每份见证先写元素个数，每个元素再写长度和内容，两个计数都用 CompactSize。示例交易 B 的结构可读作「02｜签名项长度｜签名及 01｜21｜公钥」。这里 21 是十六进制的 33；签名项的精确长度取决于实际签名字节。这一段是结构示意。卡 06 给出完整官方样例，可逐字节数。

什么时候轮到 Bob？ B 当下写入 Bob 的是输出 B:0 的花费条件。将来 Bob 再花 B:0 时，会在下一笔交易对应输入里写自己的见证。因此 Bob 收书款时不需要给 Alice 回传签名。

UTXO 是 unspent transaction output，即还可以花的一项交易输出。Bob 看到的余额来自钱包汇总它识别的输出。节点要判断某笔钱能否花，就查询具体的输出。

从历史交易算出当前余额

把旧交易按活动链顺序读一遍：每遇到一个普通输入，就按 outpoint 删掉它花费的那一项；每遇到一个可进入 UTXO 集的新输出，就按 (本交易 txid, 输出序号) 加入金额、脚本及验证所需元数据。钱包可以只跟踪和自己有关的记录，再按「我识别的脚本、是否已花费、是否已确认」筛选求和。节点维护全网可花输出；钱包可另列待确认、尚未成熟或仅观察的款项。

只看这笔书款，Bob 起初已确认 0 聪。B 入池时已确认仍为 0，待确认增加 60,000。K 接入后 B:0 转为已确认 60,000，待确认回到 0。随后，Bob 后来花掉整个 B:0，新的已确认交易不再给自己找零。这时 B 仍在历史里，B:0 对当前余额的贡献为 0。如果简单累加所有历史收款，就会重复计入已花的钱。

书款如何改变 UTXO 集？

用 (前序 txid, 从 0 起算的输出编号) 作键，这个二元组叫 outpoint。节点的链状态在该键下保存金额、scriptPubKey，以及创建高度、是否 coinbase 等验证所需信息。本例中 U 的键为 (11 重复 32 字节, 0)，值中有 100,000 聪和 Alice 的脚本。钱包还会把相关输出与自身密钥或描述符对应起来。

Bob 的节点走到哪一步 可在活动链 UTXO 集里查到什么
B 入内存池 仍能查到 U。内存池另行登记 B 占用 U
含 B 的 K 成为活动链尖 连接 K 时删除 U、写入 (txid_B,0) 的 60,000 聪和 (txid_B,1) 的 39,000 聪，假定块内无人接着花它们
若随后改采含 C 的分支 断开旧块时撤回 B 的输出、恢复 U，连接新分支时再由 C 消耗 U

B 的输入在线路上只引用 U，不携带 U 的金额。节点查到 100,000 聪后才能核对手续费 100,000 − 60,000 − 39,000 = 1,000。手续费、所有者姓名、钱包余额与确认数都无需编码成交易字段。

在原生 P2WPKH 花费中，BIP143 规定签名摘要的编码方式。本例使用 SIGHASH_ALL。

验签并拆读官方见证样例

Alice 的签名器用私钥对专题 08 的摘要签名。收到 B 的全节点只需公钥、签名和自己重算的摘要，即可核对她是否授权了这次花费。

在 secp256k1 曲线上，G 是约定的基点，n 是它的阶，私钥 d 的公钥为 Q = dG。把 32 字节摘要看作整数 z。以下大写字母表示点，小写字母表示整数，模 n 的逆元相当于这里用的除法。

  1. 签名器选取秘密的一次性标量 k（1 至 n−1），可用私钥和消息确定性地产生。算 R = kG，取 r = R 的横坐标 mod n。随后算 s = k⁻¹(z + rd) mod n，若 r 或 s 为零就重选。不同摘要复用同一 k 会危及私钥。
  2. 签名器将 r、s 编为 DER 的两个正整数。首部 30 标记序列，每个整数以 02 和长度开头，必要时在数值前补 00 保持正号。钱包通常选较小的 s 表示（low-S）。签名器再追加一个签名类型字节。
  3. B 的该输入的见证按顺序装入两项：带 01 的 DER 签名、Alice 的压缩公钥。节点先核对公钥哈希与 U 的条件匹配，再检查 r、s 的范围。以 w = s⁻¹ mod n，计算点 X = (zw mod n)G + (rw mod n)Q；X 有限且其横坐标 mod n 等于 r，验签才通过。

拿一段真实可核字节练习。 用 BIP143 官方 Native P2WPKH 向量的第二个输入（与书款 B 分开）。见证开头 02 表示两项，47 是第一项长度 71，接下来的 30 44 是 DER 序列头。该序列含两个「02 20 + 32 字节整数」，所以 DER 共 70 字节；其后的 01 才是签名类型。第二项的长度 21 表示 33 字节，公钥以 02 开头。由 02 和 21 可以确定项数和公钥长度，签名项满足 47 = 70 + 1。

验证 U 的花费既要检查公钥与 U 的哈希承诺匹配，也要用该公钥核验签名。

追踪通告、请求和交易数据

P2P（peer-to-peer，点对点）描述节点相互连接的网络结构。Bob 通常只与全网的一小部分节点直接相连。

  1. Alice 将签好的 B 提交给接入节点。这一步是钱包使用节点服务；接入节点接纳 B 后，才逐跳向愿意中继交易的邻居传播。建立 P2P 连接时双方握手，协商支持的能力。
  2. 常见路径是邻居先发 inv 通告交易标识。协商使用 wtxid 中继时，标识覆盖见证；Bob 从这条消息知道谁声称有哪笔交易。Bob 对照本地记录，已拥有的交易可跳过。
  3. 如果多个邻居通告同一标识，Bob 记录候选来源、请求时机及在途状态。Core v29.0 会考虑连接优先级、标识类型及对端的在途负载。轮到合适的来源时，Bob 发 getdata 索取交易；逾时或收到 notfound 后可从其他来源重试。
  4. 对端发来 tx 消息后，Bob 才取得可解码的交易字节，检查输入、输出和签名，再按本地策略决定入池、中继并通知钱包。就算收到十次 inv，B 仍然是零确认。矿池与矿机间的作业消息、同一台电脑内的钱包回调各有自己的通道。

被选中的邻居未返回交易数据时，节点可以向同样通告该交易的其他邻居请求。

用主网高度 170 的数据重建树根

矿池按块内交易顺序把 txid 排成一行，第一项是 coinbase。相邻两个 32 字节值按左右顺序拼接，对这 64 字节做双 SHA-256 得到父值。每层只要仍有多个值且个数为奇数，就复制该层最后一项来配对。剩一个值时，它就是写进区块头的 Merkle 根。

若 Bob 已知 B 的 txid，对方只需给每层的兄弟哈希以及 B 在树中的位置，Bob 就能逐层选对拼接方向，算到根并和 K 的头比较。这是包含证明。简化支付验证（SPV）的轻客户端还要核对区块头、工作量及后续头链，并依赖其获得的链与算力等安全假设。仅有路径不能证明 U 确实未花、B 的签名有效或块内其他交易全都有效。本例的 Bob 自营全节点，会拿块体逐笔验证。

切到主网高度 170 复算。 这个早期区块只有 coinbase 和一笔历史付款；两者都没有隔离见证。对付款提供左侧兄弟即 coinbase 的 txid 就够了。浏览器显示标识的字节顺序与内部拼接时相反。下面用 Python 3 还原为内部字节，最后翻回显示顺序。

from hashlib import sha256
coinbase = "b1fea52486ce0c62bb442b530a3f0132b826c74e473d1f2c220bfa78111c5082"
payment = "f4184fc596403b9d638783cf57adfe4c75c605f6356fbc91338530e9831e9e16"
pair = bytes.fromhex(coinbase)[::-1] + bytes.fromhex(payment)[::-1]
root = sha256(sha256(pair).digest()).digest()[::-1].hex()
print(root)
# 7dac2c5666815c17a3b36427de37bb9d2e2c5ccec3f8633eb91a4205cb4c10ff

回到含隔离见证交易 B 的 K。 块头的根来自 txid 树。为承诺见证数据，矿池还要算第二棵树：coinbase 的叶子按规定取 32 个零字节，其余交易用 wtxid。把此树根与 coinbase 输入见证里的 32 字节保留值依次拼接并做双 SHA-256，将结果写入 coinbase 的见证承诺输出（脚本开头 6a24aa21a9ed）。若有多个匹配输出，取索引最高者。coinbase 自己的 txid 又进入块头的树，因而工作量证明同样间接约束见证。

见证由 coinbase 中的见证承诺绑定。篡改见证可能保留原 txid，但重算的见证承诺不再与块中的承诺匹配。

复算创世块并推导难度调整

矿池根据候选块 K 的父链计算规定的目标，将其压缩编码填入 nBits。Bob 从同一条父链独立推算期望的 nBits，再检查哈希整数不大于解码得到的目标 T。

把哪些字节交给哈希函数？ 按线上的顺序串接版本（4 字节）、父块哈希（32）、交易 Merkle 根（32）、时间戳（4）、nBits（4）和 nonce（4），正好 80 字节。四个整数按小端序列化。常见浏览器显示的两个 32 字节哈希需逐字节反转后写入头。第二次 SHA-256 直接读取第一次的 32 字节摘要。假设每个摘要等可能，单试成功概率为 (T+1)/2²⁵⁶。T 越小，预期要试的次数越多。

主网怎样调难度？ 除创世块外，新高度不是 2016 的倍数时，沿用父块 nBits。遇到边界，取上一周期末块时间戳减首块时间戳，涵盖 2015 个间隔。把时间差限制在 3.5 至 56 天，计算 旧目标 × 限制后的秒数 ÷ 1,209,600，作整数除法，结果受主网最大目标限制，再编码为 nBits。对通常的正目标，nBits 高字节为指数 e，低 23 位为系数 m，e ≥ 3 时目标为 m × 256^(e−3)。例如 0x1d00ffff 代表 65535 × 256²⁶。节点检查目标须为正、可表示且在允许范围内。矿池把 nBits 自行放宽，即便哈希低于所填目标也通不过期望值检查。

回到 K。 ASIC 搜索的头通过 Merkle 根绑定含 B 的交易安排。为了直接复算，以下换用主网创世块头。这里的 nonce 和哈希属于创世块。

from hashlib import sha256
from struct import pack

root = bytes.fromhex("4a5e1e4baab89f3a32518a88c31bc87f618f76673e2cc77ab2127b7afdeda33b")
target = 0xffff << (8 * (0x1d - 3))
for nonce in (2083236893, 2083236894):
    header = pack("<I", 1) + bytes(32) + root[::-1] + pack("<III", 1231006505, 0x1d00ffff, nonce)
    digest = sha256(sha256(header).digest()).digest()
    print(len(header), digest[::-1].hex(), int.from_bytes(digest, "little") <= target)

创世块的区块头长 80 字节，显示哈希为 000000000019d6689c085ae165831e934ff763ae46a2a6c172b3f1b60a8ce26f，满足网络目标。

计算到期高度并对照激活条件

矿工填写块头时间，节点依据父链和本地时间分别检查。时间锁则约束一笔交易最早能在哪个块出现。

先读三个数。 候选块 K 有高度 H、有矿工自报时间；K 的父块 P 另有 MTP，即 P 和之前最多十个祖先的块头时间排序后取中位数。主网要求 K 的时间严格大于 P 的 MTP。Core v29.0 遇到超过节点当前时间两小时的头会暂不接受，待时间推进可重新检查。矿工写 K 的时间，无法单靠这个字段把本块交易的时间锁拨快。

约束 写在哪里 节点怎样核对
绝对时间锁 交易末尾的 nLockTime 0 表示没有该锁。小于 500,000,000 的正值按高度解释，其余按 Unix 秒数。至少一个输入的 nSequence 不是 0xffffffff 时，需要锁值严格小于候选块高度或父块的 MTP。全体输入均为最终序号时，交易级绝对锁不起作用。
相对时间锁 每个输入自己的 nSequence 对版本 ≥ 2 且第 31 位为 0 的输入，低 16 位给出等待量。第 22 位为 0 时按块数等待，为 1 时每单位为 512 秒。按时间时，从创建输出所在块的前一块的 MTP 起，算到候选块父块的 MTP。
CLTV、CSV 收款方可把操作码放入锁定条件，例如 P2WSH 所承诺的脚本 CLTV 要求花费交易采用匹配类型且足够大的 nLockTime，当前输入不能为最终序号。常用 CSV 条件把同类型的相对下限加到该输入，验证版本、启用位及数值。最终能否进当前块，仍要核对上面两类交易规则。

例如 U 创建于高度 900,000，花费它的 B 版本为 2，nSequence 为 3，nLockTime 为 0。高度差至少为 3，因此首次满足相对高度锁的候选块高度是 900,003。

为什么旧节点和新节点会表现不同？ 软分叉在激活后收紧有效块集合。升级节点开始拒绝违反新条件的块；只认识旧规则的节点仍可把符合新规则的块当作有效。BIP 9 给出一种历史部署方法：节点按预设周期核对版本位信号，达到条件进入锁定期，之后进入 ACTIVE 才执行新规则；超时可进入 FAILED。信号用于协调部署。实施验证仍靠各节点自己的软件，具体激活方式与参数须看该次升级。BIP 68、112、113 曾联动部署。

换算并解码金额字节

1 BTC = 100,000,000 聪（sat），所以 1 聪是 一亿分之一 BTC，即 0.00000001 BTC。千分之一 BTC 已经有 100,000 聪，恰好是 Alice 这次选中的整个旧输出 U。

这次付款中的量 聪 BTC
Alice 花掉的 U 100,000 0.00100000
Bob 的书款 B:0 60,000 0.00060000
Alice 的找零 B:1 39,000 0.00039000
输入减去输出的手续费 1,000 0.00001000

怎么用。 从 BTC 换成聪就乘一亿，反向换算除以一亿。钱包可以切换显示单位。写入普通交易输出时，金额按整数聪编码，另有脚本规定这笔钱以后怎样花。节点读到的 B:0 前八字节是小端序的整数。用 Python 的 int.from_bytes(bytes.fromhex("60 ea 00 00 00 00 00 00"), "little")，结果为 60000。手续费 1,000 聪没有单独的输出，节点通过已知的 U 和两个输出求差。

钱包显示的 60,000 聪和 0.00060000 BTC 对应相同的交易金额字节。

沿付款、入池与首次确认对照两者

钱包回答「哪些钱由我控制，我要付给谁，我收到多少」。全节点回答「按我独立验证的历史，这个输出能否花，这个区块能否接入」。Bob 同机运行两者，所以一根本地通知箭头就能把后一个答案交给前者。

停在何处 钱包读写什么 全节点读写什么
Alice 扫码并提交 B 从自己的付款记录选 U，生成两项输出，让控制 U 的密钥签名，交出带见证的 B 接入节点查 U、核对脚本和费用，按本地策略决定是否入池并中继
Bob 第一次从邻居看到 B 钱包得到入池通知，用自己的收款脚本认出 B:0，登记 60,000 聪待确认 节点的内存池登记 B 引用 U；当前活动链 UTXO 中仍然有 U
Bob 接入包含 B 的 K 钱包记录 B 所在的块，从活动链位置算出首次确认 节点按父块状态验 K，接入活动链时花掉 U、加入 B:0 和 B:1，通知钱包

钱包能识别输出与能签名是两种能力。观察钱包只凭收款脚本也能跟踪 Bob 的钱；要花 B:0 时才需要相应的签名能力。运行全节点的人可以不加载任何钱包，也无需参与挖矿。没有 Bob 的私钥，他的节点依然能验证 Bob 将来花 B:0 时提供的签名。

Bob 也可能首次在 K 中看到 B。节点用父块状态验块，接入后钱包可直接显示 1 次确认。
